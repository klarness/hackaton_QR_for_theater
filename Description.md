# Краткое содержание 

Проект разделим на два параллельных направления: **фронтенд** (мобильный веб-клиент с AR) и **бэкенд** (API и БД). Фронтенд будет на JavaScript с React, используя Three.js и React Three Fiber для рендеринга 3D, MindAR или AR.js для трекинга маркеров и html5-qrcode для сканирования QR. Бэкенд на Node.js/Express (или NestJS) с PostgreSQL (или аналогичной СУБД) для хранения прогресса квестов. Это позволит быстро прототипировать за счёт единого языка (JS). Структурно браузер запрашивает камеру, сканирует QR (html5-qrcode), загружает контент AR (MindAR) и рендерит персонажа (Three.js). Прогресс квеста и диалоги передаются через REST/WebSocket к серверу и сохраняются в БД. Основной MVP-задачей первого дня будет: открыть сайт, дать разрешение на камеру, навести на маркер → отобразить простую анимированную 3D-модель. В дальнейшем добавим логику квестов, диалоги и оптимизацию. Ниже приведён детальный план, архитектура, API, схемы БД, чек-листы тестирования и оптимизации, а также риски и задачи первого дня.

## Рекомендуемый стек и технологии

- **Фронтенд:** React с Vite (быстрый старт); Three.js и [React Three Fiber (r3f)](https://docs.pmnd.rs/react-three-fiber/getting-started/introduction) для 3D в React; `@react-three/drei` для вспомогательных компонентов; Zustand или Redux для состояния (в частности, прогресса квеста);  
- **AR-трекинг:** **MindAR** или **AR.js**. AR.js легковесен и хорошо работает на большинстве устройств, однако поддерживает только традиционные маркеры. MindAR новее и кроме маркеров умеет распознавать изображения и лица, что даёт гибкость, но чуть сложнее в настройке. На iOS Safari прямой WebXR-AR нет, поэтому используем маркеры (через MindAR или AR.js) для всех платформ.  
- **Сканирование QR:** библиотека [html5-qrcode](https://github.com/mebjas/html5-qrcode) (поддерживает моб. и десктоп, позволяет запрашивать камеру и декодировать QR).  
- **Бэкенд:** Node.js с Express/NestJS (или Fastify) – быстрое прототипирование, единый язык. Node.js хорошо обрабатывает I/O и реальное время. В будущем на продакшене можно перейти на Go (Gin/Echo) для более высокой производительности, но для хакатона Node предпочтительнее.  
- **База данных:** PostgreSQL (или MySQL). Реляционная СУБД хорошо подходит для схемы квестов и прогресса. Для прототипа можно использовать SQLite/JSON-файлы, но лучше Postgres из-за масштабируемости.  
- **Хранение ассетов:** AWS S3 (или DigitalOcean Spaces) для 3D моделей (.glb) и текстур, с CDN. Или статика вместе с фронтендом при простом размещении (Netlify, Vercel).  
- **Реальное время:** Socket.IO или WebSocket для фич реального времени (если понадобится), например, чтоб в будущем несколько пользователей видели общие события. Для MVP достаточно REST/API.  

**Почему React+Three.js:** React позволяет описывать UI и 3D-сцену декларативно. Библиотеки r3f и drei дают знакомый React-подход к Three.js, ускоряя разработку (компоненты `<Canvas>`, `<mesh>`, `<PerformanceMonitor>` и т.п.). React дает общий код для веб, мобильных и XR.  

**Сравнение Node.js и Go:** Node.js проще для такого проекта благодаря экосистеме npm и единому языку (JS). Для хакатона это ключевое преимущество – нет переключения языков. Go очень быстр и хорошо масштабируется, но для прототипа лишние сложности и меньше библиотек. (В продакшене можно рассмотреть Go для высоких нагрузок и коннкуррентной обработки, но не в рамках срочного MVP.)  

## Архитектура системы и компоненты

```mermaid
flowchart TD
  User[Пользователь] -->|Открывает сайт (HTTPS)| Frontend[Веб-приложение (React)]
  subgraph Фронтенд
    Frontend -->|Запрашивает доступ к камере| Camera[Camera API]
    Camera --> QRScanner[html5-qrcode]
    QRScanner -->|распознал QR| Navigator[React Router/JS]
    Navigator --> ARModule[MindAR / AR.js (трекинг)]
    ARModule --> Three[Three.js + React Three Fiber]
    Three -->|отрисовка| Model[3D-модель (.glb)]
    Three --> Anim[Анимация модели]
    Frontend --> UI[React UI (диалоги, кнопки)]
    UI -->|запросы| Backend[Backend API]
  end
  subgraph Бэкенд
    Backend --> DB[(PostgreSQL)]
    Backend --> Storage[(S3/Cloud Storage)]
  end
  Storage -->|хранит модели| Model
```

**Основные компоненты:**

- **Камера/QR:** браузер вызывает `navigator.mediaDevices.getUserMedia`, html5-qrcode рисует видео и сканирует QR.  
- **AR-модуль:** либо MindAR (`mindar-image-three`) либо AR.js. Они берут видеопоток и отслеживают заранее сгенерированный маркер (image-target). MindAR добавляет обёртку для Three.js. ARModule сигнализирует Three.js об обнаружении маркера и даёт матрицу трансформации.  
- **Three.js + React Three Fiber:** рендерит 3D-сцену в `<Canvas>`. При наведении на маркер рисуется 3D-модель персонажа с анимацией. Можно использовать `<primitive object={gltf.scene}>` для модели.  
- **React UI:** отображает элементы интерфейса (кнопки “Начать квест/Поболтать”, текст диалога), управляет состоянием (`Zustand` или `useState`).  
- **Backend API:** REST(или GraphQL) на Express, обрабатывает запросы о квестах и диалогах.  
- **База данных:** хранит прогресс пользователей, статические данные о квестах, персонажах и предопределённых репликах.  
- **Хранилище ассетов:** статические файлы 3D-моделей и текстур. Можно хранить в облаке (S3) и отдавать через CDN.

## Дизайн API 

Примерная схема REST API (JSON):

- **GET /api/characters/:id** – получить данные персонажа (имя, URL модели, параметры):  
  **Ответ:**  
  ```json
  {
    "id": "dragon",
    "name": "Дракон",
    "modelUrl": "https://cdn.example.com/models/dragon.glb",
    "animations": ["idle", "talk"]
  }
  ```
- **POST /api/quests/start** – начать квест. Тело: `{ "userId": 1, "characterId": "dragon" }`.  
  **Ответ:** `{ "questId": 5, "currentStep": 1, "nextCharacter": "wizard", "isCompleted": false }`.  
- **GET /api/quests/:userId** – получить текущее состояние квеста пользователя.  
- **PUT /api/quests/:userId** – обновить прогресс. Тело: `{ "questId":5, "step":2, "status":"in_progress" }`.  
- **POST /api/dialog** – обработать действие в диалоге. Тело: `{ "questId":5, "characterId":"dragon", "userMessage":"Я готов к следующему заданию." }`.  
  **Ответ:** `{ "npcReply": "Иди к волшебнику у подножия горы.", "nextCharacter": "wizard", "step": 2 }`.  

*Пример JSON-запроса:*
```json
POST /api/dialog
{
  "userId": 1,
  "characterId": "elf",
  "userReply": "Спасибо, до встречи!",
  "questStep": 3
}
```
Ответ может выглядеть так:
```json
{
  "npcReply": "Удачи в поиске древнего артефакта!",
  "nextQuestStep": 4,
  "questComplete": false
}
```

## Схема данных (пример таблиц)

| Таблица           | Поля (тип, описание)                                                                                  |
|-------------------|-------------------------------------------------------------------------------------------------------|
| **users**         | id (PK), name, email (опционально), ...                                                              |
| **characters**    | id (PK), name, model_url, default_animation, ...                                                      |
| **quests**        | id (PK), name, description, start_character_id (FK), end_character_id (FK)                            |
| **quest_steps**   | id (PK), quest_id (FK), step_number, description, character_id (кто дает задание), next_step_id (FK) |
| **quest_progress**| id (PK), user_id (FK), quest_id (FK), current_step (FK), current_character_id, status, updated_at      |
| **dialogues**     | id, character_id (FK), npc_text, user_options (JSON-массив предустановленных ответов)                 |

- **characters**: хранит персонажей (например, драг, эльф) с ссылкой на 3D-модель.  
- **quests** и **quest_steps**: задают структуру квеста, какие персонажи участвуют, тексты заданий.  
- **quest_progress**: текущий прогресс (какой шаг, какой персонаж сейчас).  
- **dialogues**: фиксированные фразы NPC и варианты ответов пользователя (для режима “Поболтать”). Можно хранить JSON с вариантами ответов.

## MVP-чек-лист и тестовая матрица

**MVP-чек-лист:**  
- [ ] Приложение запускается по HTTPS (безопасный контекст).  
- [ ] Запрашивается и получено разрешение на камеру.  
- [ ] QR-сканер обнаруживает код и запускает AR-сцену (либо переходит по ссылке).  
- [ ] Над маркером отображается 3D-модель персонажа (а) и анимация (idling).  
- [ ] Кнопка **“Начать квест”** запрашивает API и отображает подсказку о следующем персонаже.  
- [ ] Кнопка **“Поболтать”** запускает диалог: NPC говорит фразу, пользователь выбирает ответ (или вводит), NPC отвечает.  
- [ ] Прогресс квеста сохраняется в БД (после рестарта все состояния восстанавливаются из API).  
- [ ] UI адаптивен для мобильного (скролл в `#container`, без неожиданных зумов).

**Тестовая матрица:**  
| Устройство        | Браузер         | Тестовый сценарий                                                  |
|-------------------|-----------------|--------------------------------------------------------------------|
| Android (Chrome)  | Chrome Mobile   | Камера активируется, сканирует QR, запускает AR. 3D модель видна.  |
| Android (Samsung) | Samsung Browser | То же, тестировать на разных моделях.                              |
| iPhone (iOS 15+)  | Safari          | Камера работает, но WebXR не поддерживается; проверить QuickLook (USDZ). Вывести сообщение о неподдерживаемом AR. |
| iPhone (iOS 14)   | Safari          | Старая версия не даёт доступа к камере, протестировать поведение (ошибка или fallback). |
| iPad              | iOS Safari      | Аналогично iPhone.                                                 |
| Desktop (Windows) | Chrome          | Использовать веб-камеру или загрузку изображения для QR (html5-qrcode поддерживает этот режим). 3D-сцена должна отображаться (как эмуляция AR). |
| Desktop (macOS)   | Chrome/Firefox  | То же (камеры обычно).                                             |

**Кейсы отказа:**  
- Пользователь отклоняет доступ к камере. *Mitigation:* показать понятное сообщение “Чтобы увидеть персонажа в AR, разрешите доступ к камере.”  
- Маркер не распознался (темнота, размытость). *Mitigation:* подсвечивать область сканера, давать инструкции (“держите камеру ближе”).  
- Слабое CPU/GPU: тест на слабых телефонах (средство отображения fps). При падении FPS снижать детализацию (см. Optimization ниже).

## Производительность и оптимизация для мобильных

Мобильные устройства ограничены по памяти и GPU. Рекомендации:

- **Размер моделей:** стремиться к небольшим .glb (несколько мегабайт). **Декомпозиция:** сложную модель можно разбить на части и загружать по мере необходимости.  
- **Draco-компрессия:** использовать [Draco](https://google.github.io/draco/) для геометрии. Как отмечено, Draco может уменьшить размер модели на 90–95%. Разжатие выполняется в WebWorker, не блокируя главный поток.  
- **Компрессия текстур:** использовать KTX2/Basis Universal. JPEG/PNG при загрузке создают большие текстуры; KTX2 остаётся сжатым в памяти и может уменьшить VRAM в ~10 раз. Инструмент [gltf-transform](https://gltf-transform.donmccurdy.com/) поможет автоматизировать сжатие (`gltf-transform draco ...`, `gltf-transform unlit`).  
- **Level of Detail (LOD):** для каждого персонажа подготовить несколько версий модели (high/med/low-poly). В React Three Fiber есть компонент [`<Detailed distances=[...]>`](https://docs.pmnd.rs/drei/api-components/detailed) из drei – он самостоятельно переключает модель по дистанции. Это снижает нагрузку при удалении камеры или низком zoom.  
- **Ленивая загрузка (Lazy load):** загружать модели и текстуры только перед отображением. Например, использовать `React.lazy` или динамический `import()`, показывая спиннер в ожидании. Диалоги и данные квестов можно тоже загружать по запросу.  
- **Текстуры малого размера:** для MVP текстуры можно упростить (512×512 или меньше) и удалить ненужные (normal-map только если критично).  
- **Оптимизация сцен:** минимизировать количество источников света (например, один AmbientLight + DirectionalLight), избегать громоздких шейдеров. Использовать `meshStandardMaterial` без лишних настроек.  
- **Проверка производительности:** компоненты `<PerformanceMonitor>` или `stats.js` помогут отследить FPS.  

Соблюдение этих рекомендаций обеспечит плавность на мобильных. Например, сжатие и LOD могут дать заметный выигрыш FPS.

## Развертывание и CI/CD

- **Хостинг фронтенда:** можно публиковать как статический сайт (Netlify, Vercel, GitHub Pages + Cloudflare), раздавая React-бандл и ассеты. Обязательно HTTPS (WebXR требует безопасного контекста).  
- **Хостинг бэкенда:** Heroku, Render.com или VPS (AWS/GCP/Azure). Использовать Docker-контейнеры или Node-процесс.  
- **CDN для моделей:** 3D-файлы(.glb) поместить на CDN (Amazon S3 + CloudFront или аналог) для быстрой загрузки.  
- **CI/CD:** GitHub Actions или другой CI: запускать линтеры (ESLint), unit-тесты (Jest) и после успешного билда деплоить. Автоматически разворачивать фронт и бэк при пуше в main.  
- **Мониторинг:** логирование (Loggly, Sentry), если критично.  
- **Резервное копирование:** настроить бэкапы БД (PostgreSQL имеет встроенные инструменты бекапа).  
- **Безопасность:** использовать Helmet/CORS, ограничение частоты запросов (rate-limiter). Вынести секреты в переменные окружения.

## Приоритетные риски и их минимизация

1. **Поддержка Safari/iOS:** WebXR AR в Safari официально не поддерживается. Риск – невозможность обычного AR-представления на iPhone. *Mitigation:* использовать маркер на экране без true AR, либо обходные решения (Apple AR Quick Look с USDZ, либо 8th Wall-подход, но это платно). По минимуму – показывать 3D-модель на экране и предупреждать, что AR недоступен на iOS.  
2. **Производительность на слабых устройствах:** тяжёлые модели, текстуры, обработка видео. *Mitigation:* применять компрессию Draco/KTX2, LOD, ленивая загрузка и тестировать заранее.  
3. **Отказ камеры:** пользователь может не дать разрешение. *Mitigation:* показывать инструкцию («Нажмите Разрешить, чтобы использовать камеру»). Вариант оффлайн – дать загрузить QR-изображение как файл через html5-qrcode.  
4. **Плохая видимость маркера:** маркер плохо распознаётся (повышенный шум, движение). *Mitigation:* подсказки в UI (“держите камеру неподвижно, просветите маркер”). Использовать крупный чёткий маркер с контрастной рамкой.  
5. **Нестабильная связь/API:** проблемы сети. *Mitigation:* кеширование прогресса локально (IndexedDB) или ретраи при ошибках. Фронт должен корректно обрабатывать ошибки API (например, показывать сообщение “ошибка сервера”).  
6. **Время загрузки:** много ресурсов. *Mitigation:* асинхронная загрузка ассетов, минификация JS/CSS, HTTP2/3.  
7. **Согласованность прогресса:** несколько сцен или длительный квест. *Mitigation:* атомарные обновления в БД и явные статусы (finished/in_progress) для каждого шага.  

## Конкретные задачи первого дня и команды

**Разработчик 1 (Frontend/AR):**
1. Создать проект React:  
   ```bash
   npm create vite@latest my-ar-app --template react
   cd my-ar-app
   npm install three @react-three/fiber @react-three/drei mindar-image-three html5-qrcode axios zustand
   ```  
2. Настроить компоненты: `<CameraScanner>` с html5-qrcode для захвата QR; `<ARViewer>` для активации MindAR.  
3. Проверить, что камера включается:  
   ```js
   const html5QrCode = new Html5Qrcode("reader");
   html5QrCode.start({ facingMode: "environment" }, { fps: 10 }, onSuccess);
   ```  
   *Событие onSuccess* выводит текст QR.  
4. Добавить MindAR: подключить скрипт (или пакет `mindar-image-three`). Сделать контейнер с `<MindARImage>` и примитив (плоскость или модель).  
5. Отобразить тестовую GLB-модель над маркером:  
   ```js
   const gltf = useLoader(GLTFLoader, "/models/character.glb");
   anchorGroup.add(gltf.scene);
   ```  
6. Настроить базовый UI: панель с кнопками «Начать квест» / «Поболтать» (React state).  
7. Коммит изменений.

**Разработчик 2 (Backend/API):**
1. Инициализировать сервер:  
   ```bash
   mkdir backend && cd backend
   npm init -y
   npm install express cors pg axios
   ```  
2. Настроить Express-сервер (`server.js`) с CORS и JSON:  
   ```js
   const express = require('express');
   const app = express();
   app.use(express.json());
   app.use(cors());
   app.listen(3000);
   ```  
3. Подключить PostgreSQL (через `pg`) и создать таблицы (users, quests, progress).  
4. Реализовать тестовый роут:  
   ```js
   app.get('/api/health', (req, res) => res.json({ status: 'ok' }));
   ```  
5. Реализовать заглушки API квеста: `POST /api/quests/start` (генерация id, отправка ответа с начальным шагом), `GET /api/quests/:userId`. Тестировать с помощью Postman/insomnia.  
6. Подготовить схему БД (SQL-скрипт или ORM) для quest_progress.  
7. Коммит.

После этого каждый из разработчиков проверяет связь: фронт отправляет запрос `/api/health`, получает `{status:'ok'}`.

## Вопросы и предположения

- **Учёт пользователей:** Планируем ли вводить систему аккаунтов? Или все пользователи анонимны (localStorage)? Это влияет на хранение `userId` и на необходимость авторизации.  
- **Уникальность QR-маркеров:** Будет ли каждый персонаж привязан к своему QR? Или один URL с параметром? (Маркировать каждого персонажа отдельным ID удобнее.)  
- **Мультиплеер:** Нужен ли совместный режим (несколько пользователей в одной AR-сцене)? Влияет на архитектуру (Socket.IO). Скорее всего – нет для MVP.  
- **Диалоги:** Предусмотрены ли только предустановленные фразы? Планируется ли ИИ (LLM) для ответов? На хакатоне лучше ограничиться статическими диалогами.  
- **Голосовой ввод/вывод:** Нужен ли озвученный диалог (Speech Synthesis/Recognition)? Это усложнит MVP.  
- **Перемещение NPC:** Будут ли персонажи двигаться по сцене? (Тогда нужны пути, анимация ходьбы.) Если нет – статический AR-объект.  
- **Поддержка оффлайн:** Интернет всегда есть? Если нет – кэшировать модели и диалоги для offline.  

Этот отчёт содержит подробный пошаговый план разработки и обоснование каждого выбора, что позволит команде эффективно реализовать указанный функционал. Использованы актуальные источники и рекомендации по WebAR, 3D и веб-разработке.
